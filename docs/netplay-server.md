# Melee relay and room lists

Status: private alpha. Two browser pages have completed local online-combat
checks. The public relay at https://urquanmasters.org is the Cloudflare port
described below. Live matches between a Mac and a GitHub runner on a different
network passed for both editions on 2026-10-19.
See [the original validation record](validation.md) and
[the Rust validation record](rust-validation.md) for the edition and build
covered by each completed check.

The local server serves the built game and connects exactly two players in each room. It relays ordered binary game data; the UQM engine validates its own protocol and synchronizes the match. It does not proxy TCP connections or connect to arbitrary destinations. There are two local servers with the same room protocol: the Node server (`npm start`, `server/netplay.mjs`) and the Rust server (`npm run start:rust`, `rust/uqm-relay`).

The Node server and the Cloudflare relay also keep a **room list (lobby)** for
each edition: a host can give a room a name, and other players see the named
rooms that wait for a guest and pick one. See [Room lists](#room-lists). The
Rust server does not have room lists yet: it refuses lobby sockets and named
rooms, and its private rooms work as before. For this reason `npm start` runs
the Node server.

## Run locally

Requires Node.js 22 or newer (and Rust 1.85.1 for the Rust server, as
described in [the Rust build guide](rust-port.md)). From the project directory:

```sh
npm ci
npm start
```

Open `http://127.0.0.1:9999/`. The game must already be built in `dist/` using `scripts/build-web.sh`. The server sends the COOP/COEP headers required for WebAssembly threads. If the older Python preview is using port 9999, use `npm start -- --port 10000` and open that port. The Python preview and the legacy nginx Docker image do not provide multiplayer rooms; use this relay for Online Melee. `npm run start:rust` compiles and runs the Rust server, which takes the same options; once built, `rust/target/release/uqm-relay` runs directly without Node or Cargo.

Use `scripts/build-editions.sh` to place both editions behind the picker in
`dist/`, or `--dist .tools/hd-dist` to serve a standalone HD build. Both editions
can use the same relay at the same time. On the chosen edition's page, choose
**Online Melee** on the start screen (or press O in the main menu), then
**Create room**. The room shows in the lobby of every player of that edition;
a player chooses it in the list, or opens the invitation link. The match starts
when both players are in the room (see `docs/online-ui.md`).
The full invitation retains the edition page, such as `/hd/index.html#room=…`.
Original players can play Original players; HD players can play HD players.

```sh
npm test
```

The server tests use actual WebSocket clients and ephemeral loopback ports. They cover pairing, bidirectional exact byte order, deterministic delay/jitter, isolation between rooms and editions (including identical tokens), independent token retirement, shared capacity limits, URL/origin validation, duplicate roles, early/invalid/oversized data, queue bounds, rate limits, disconnects, room expiry, heartbeat, ping/pong flooding and paused-reader backpressure, and static file traversal protection. They do not establish that a full UQM match remains synchronized; that requires the game integration tests and real browser play. After a full
build, `npx playwright install chromium` and `UQM_RELAY=rust npm run test:browser` run the
real game in two independent Chromium processes with a temporary relay,
including simulated delay/jitter and abrupt peer disconnects. Results are
written to `test-results/browser/`; see [validation](validation.md).

For a standalone HD build, run:

```sh
UQM_EDITION=hd UQM_RELAY=rust UQM_DIST=.tools/hd-dist \
  UQM_TEST_OUTPUT=test-results/hd-netplay npm run test:browser
```

Set `UQM_PEER_DIST` to an independent HD C-reference package to compare Rust
and C through the same relay. Do not mix an HD engine and an Original engine
in one test. See [the Rust verification commands](rust-port.md#verification).

## Connection contract

The endpoints are:

| Edition | WebSocket request path |
| --- | --- |
| Original 3DO | `/netplay/<room>?role=host` or `?role=guest` |
| Redrawn HD | `/netplay/hd/<room>?role=host` or `?role=guest` |

A host can add `name` and `engine` (see [Room lists](#room-lists)). No other
query parameters, no parameter twice, and no WebSocket subprotocol are
accepted. A room token must be exactly 32 lowercase hexadecimal characters generated by the
browser with `crypto.getRandomValues` (128 random bits). Active rooms and retired
tokens are identified by **edition plus token**. Using the same token in both
editions creates independent rooms; their players cannot pair or exchange data.

A host creates a room. A guest can join only an existing waiting room. Each accepted participant receives `{"type":"waiting"}`. Once paired, both receive `{"type":"ready","role":"host"}` or `{"type":"ready","role":"guest"}`. Only then may either send nonempty binary WebSocket messages, up to 65,536 bytes per message. Packet boundaries are independent of WebSocket message boundaries. Text is reserved for server notifications and is never accepted as game data.

Connection errors are sent as `{"type":"error","message":"…"}` and close the offending connection. An invalid Origin, unsupported subprotocol or exhausted global connection limit is rejected during the HTTP upgrade, before a WebSocket exists. On disconnect, the survivor receives `{"type":"peer-left","message":"…"}` and is closed. A third client cannot displace a player. Closing either player retires that edition's room token for the lifetime of the server process; reconnecting requires a newly generated room. It does not close or retire the other edition's room with the same token. Room state and retirement records are in memory, so a server restart ends all rooms and clears those records.

The invitation link is the room capability: somebody who obtains it can occupy the guest slot before the intended guest. A named room publishes its token in the room list, so any player of that edition can take its guest slot; a room without a name stays private. There are no accounts or persistent match records. The server does not log invitation tokens or game data.

Browsers cannot send WebSocket ping frames. A client may send the text message
`ping` at any time; the relay answers with the text `pong` and does not treat
it as game data. The browser client sends it every 30 seconds while a named
room waits and while it watches a room list. On the Node server these texts
count against the control-frame quota below.

## Room lists

A room list is a read-only WebSocket per edition:

| Edition | Room list WebSocket path |
| --- | --- |
| Original 3DO | `/netplay/lobby?edition=original` |
| Redrawn HD | `/netplay/lobby?edition=hd` |

The Origin and subprotocol checks are the same as for rooms. On connect, and
again whenever the list changes, the server sends a full snapshot, newest
first, at most 50 rooms:

```json
{"type":"rooms","rooms":[{"id":"<32 hex token>","name":"Friday duel","engine":"c","created":1760950000000}]}
```

`engine` is `"c"`, `"rust"` or `null`; `created` is the creation time in
milliseconds since the Unix epoch. Snapshots go out at most twice a second to
all watchers; the last change always goes out. The list accepts no messages
except `ping`: any other message closes the socket with code 1008.

A host creates a **named (listed) room** with the normal room URL and two more
parameters:

```
/netplay/<token>?role=host&name=<URL-encoded name>&engine=c|rust
/netplay/hd/<token>?role=host&name=<URL-encoded name>&engine=c|rust
```

- `name` is required for a listed room. `+` decodes to a space. The relay
  normalizes the name to NFC, changes each run of spaces to one space and
  trims it; the list shows that form. The result must have 1 to 24 characters
  (Unicode code points) with at least one letter, digit, punctuation mark or
  symbol. These are refused: control and format characters (such as bidi
  overrides and zero-width marks), line separators, surrogates, private-use and
  unassigned code points (also noncharacters), the blank fillers U+115F,
  U+1160, U+2800, U+3164 and U+FFA0, and more than 3 nonspacing marks in a row
  in the decomposed (NFD) form. Hebrew with niqqud needs 3; Zalgo text needs
  more. Otherwise the host gets `{"type":"error","message":"Room names need 1
  to 24 visible characters."}`. The client's `UQMNetplay.roomName()` applies the
  same rule; `sc2/wasm/tests/room-names.cjs` holds the shared test cases. Names
  can still be wide (for example U+FDFD), so a page that draws the list must fit
  each name to its row.
- `engine` is optional and allowed only together with `name`.
- Guests use the normal `?role=guest` URL with no other parameter.

The room enters the list once its host is connected, and leaves it when a guest
joins, when the host leaves, or when the room fails or expires. A listed room
waits 10 minutes for a guest; a private room waits 2 minutes. When the list is
full (50 rooms of that edition) or the host's address already has 3 waiting
listed rooms, the host gets an error message and the token stays usable.

A listed host sends the text `ping` every 30 seconds while it waits (the
browser client does this). When a listed host sends no `ping` for 150 seconds,
the relay closes the room with `{"type":"error","message":"The room closed
because this page stopped answering. Create a new room."}` and the room leaves
the list. This finds sleeping computers, lost networks and frozen pages, which
the TCP connection or protocol pings do not show at once. A guest who picks
such a room before the liveness check finds it gets "Room does not exist or has
expired." and never pairs. 150 seconds allows for background tabs, whose
timers can run only once a minute. Private rooms are not checked: they do not
ping.

List tokens are public, so one address may join at most 10 listed rooms in 10
minutes. Further joins get "You joined many open rooms in a short time. Wait a
few minutes, then try again." and the room keeps waiting. Joins of private
rooms (with an invite) are not counted.

## Browser client API

`sc2/wasm/netplay-client.js` exposes `UQMNetplay`:

- `UQMNetplay.watchLobby({ edition, onRooms(rooms), onStatus(state, message) })`
  returns `{ close(), state, rooms }`. `edition` is `'original'` (default) or
  `'hd'`. `onRooms` gets every checked snapshot as
  `[{ id, name, engine, created }]`. `state` is `'connecting'`, `'open'` (the
  list is live), `'error'` (the connection failed or was lost; the watcher
  reconnects after 1, 2, 4, 8, then every 15 seconds and reports `'open'`
  again) or `'closed'` (after `close()`, or on a page outside a web server).
  It pings every 30 seconds and reconnects when a ping gets no answer.
  A named host also pings every 30 seconds while it waits; when a ping gets no
  answer, its room client reports `'error'` with "Lost the connection to online
  play. Create a new room." Relay errors for a host are shown as the relay
  sends them; for a guest they start with "Could not join this room."
- `UQMNetplay.connect({ token, role: 'host', edition, name, engine, onStatus })`
  creates a listed room; without `name` the room is private. `engine` is sent
  only with a name. Join a listed room with
  `UQMNetplay.connect({ token: room.id, role: 'guest', edition })`.
- `UQMNetplay.roomName(text)` returns the name as the list will show it
  (NFC, one space between words, trimmed) or throws the message for the
  player; `UQMNetplay.limits.roomNameChars` is 24. A page can call it to check
  a name before it creates the room.
- `UQMNetplay.lobbyURL(edition)` and `UQMNetplay.relayURL(token, role,
  location, edition, { name, engine })` build the socket URLs.

`npm run test:lobby-client` runs this API in Chromium, Firefox and WebKit
against the Node server (no game build needed): one page watches the HD room
list, a second page creates a named room, and the first page picks it from the
list and receives game data. Set `UQM_BROWSERS=chromium` for one browser.
Screenshots go to `test-results/lobby-client/`.

## Bounds

Default bounds are 128 active rooms, 16 connections per IP, 10,000 distinct room IDs per server process, 64 KiB per WebSocket message, 256 KiB of outgoing/queued data per direction, and at most 1,000 messages or 1 MiB per second per player. Compression is disabled. New rooms stop being accepted when the distinct-ID bound is reached; existing rooms continue. Restart the server to reset that bound.

Room lists: at most 50 listed rooms per edition, 3 waiting listed rooms per
address and 10 listed-room joins per address in 10 minutes. Room-list sockets
have their own bounds: 10 per address and 256 in total on the Node server (10
per address and 1,000 per edition on Cloudflare), and 1 KiB per received
message. They do not count against the room connection limits. A reader too
slow for a snapshot is disconnected; its client reconnects for a fresh one.

**Address** in every per-address bound (connections, listed rooms, joins,
room-list sockets) means an IPv4 address, or for IPv6 the /64 network: one
IPv6 client controls a whole /64, so it could otherwise fill the list. An
IPv4-mapped IPv6 address (`::ffff:192.0.2.1`) counts as its IPv4 address.

Room, retired-ID and connection limits are shared across editions. An Original
room and an HD room with the same token consume two room identities.

Ping and pong control frames have a separate default quota of 32 frames and
4 KiB per second, counting the two-byte frame header. Replies to client pings
also respect the outgoing buffer bound. The frame quota increases only when
tests explicitly configure a heartbeat faster than the normal 15 seconds.

A waiting room expires after two minutes, a listed (named) waiting room after ten minutes. Paired rooms expire after 15 minutes without game data or four hours total. A ping/pong heartbeat runs every 15 seconds. Slow peers, rate violations, missing pongs and expired rooms are disconnected. No game data is queued before pairing, and a disconnected room's pending data is discarded.

## Two computers and later hosting

The default bind address is loopback. Binding another interface is explicit:

```sh
npm start -- --host 0.0.0.0 --port 9999
```

Browsers need a secure context for WebAssembly shared memory: plain HTTP on a LAN IP is insufficient even with isolation headers. For two computers, put this server behind a trusted HTTPS reverse proxy with WebSocket upgrades enabled, and pass the exact browser-facing origin:

```sh
npm start -- --host 127.0.0.1 --port 9999 --origin https://game.example
```

Forward the whole `/netplay/` subtree, including `/netplay/hd/`, to this relay.
Serving the HD static files alone does not provide HD rooms.

`--origin` can be repeated for a finite allowlist. Without it, requests must have an Origin matching the request's own HTTP(S) origin. Missing origins, `null`, wildcard values and trailing slashes are rejected. Forwarded headers are not trusted to determine origins or client IPs; a reverse proxy may therefore share the default per-IP connection limit. Do not expose a proxy configuration until its own TLS, upgrade forwarding and isolation headers have been checked.

`--dist /absolute/path/to/built-game` selects a different static document root. Only GET and HEAD requests for regular files inside that root are served. Hidden paths, directory listings, traversal and symlinks escaping the root are rejected.

## Cloudflare relay (urquanmasters.org)

The public site runs the same relay contract as a Cloudflare Durable Object
([deploy/netplay.js](../deploy/netplay.js)). The Worker sends `/netplay/*` to it
with the full path and query. The browser client is the same.

- The Worker checks the upgrade, the exact Origin (`https://urquanmasters.org`;
  the `NETPLAY_ORIGINS` var changes it for tests), subprotocols and the room URL
  before a room object is involved. These failures give the same responses as
  the Node server.
- Each room ID has one `NetplayRoom` object. It holds both WebSockets with the
  hibernation API, so a quiet room costs nothing between messages. One alarm
  covers the waiting expiry (2 min), the idle limit (15 min) and the total
  lifetime (4 h).
- An ended room keeps a retired marker for 7 days, then deletes its storage.
  Within that time the room ID cannot be used again. A deploy restarts all
  objects and closes all open rooms.
- One `NetplayGate` object holds a lease for each open connection. It enforces
  16 connections per client address, 256 connections and 128 active rooms in
  total. The client address is `CF-Connecting-IP`, which the Cloudflare edge
  sets; the Worker changes it to the per-address key (IPv4 address or IPv6
  /64) before any object sees it. If a connection ended without a close event,
  the gate asks its room before it refuses a client, and every lease expires
  after the room lifetime. The gate also counts listed-room joins per address,
  in memory only: the object stays in memory while an address keeps joining.
- The game-data rules (pairing first, nonempty binary only, 64 KiB per message
  with close code 1009, 1,000 messages or 1 MiB per second) are the same.
- One `NetplayLobby` object per edition (`lobby:original`, `lobby:hd`) holds
  the listed rooms (in its storage, so a hibernated object reloads them) and
  the room-list sockets (hibernation API, tagged by `CF-Connecting-IP` for the
  per-address bound). A room object adds its room when the named host is
  connected, and removes it when the room pairs or ends. While rooms are
  listed, an alarm every 20 seconds asks each room object whether its room
  still waits with a connected host that pings, and drops the others (for
  example rooms whose objects a deploy restarted) and entries older than the
  10-minute limit. A room object whose host is silent closes its room when it
  is asked. A list that is full asks the rooms the same way before it refuses a
  host, at most once every 5 seconds; other refusals in that time use the last
  result. Room-list sockets and rooms answer the text `ping` in the runtime
  (`setWebSocketAutoResponse`), without waking the object. A room object reads
  the time of its host's last `ping` with `getWebSocketAutoResponseTimestamp`.
  The class was added with the migration `netplay-v2`.
- The lobby stores each listed host's address key (IPv4 address or IPv6 /64)
  with its entry, for the per-address bound, until the room leaves the list.
  Snapshots never contain it.
- Test vars: `NETPLAY_LISTED_WAITING_MS`, `NETPLAY_MAX_LISTED`,
  `NETPLAY_MAX_LISTED_PER_IP`, `NETPLAY_MAX_LOBBY`, `NETPLAY_MAX_LOBBY_PER_IP`,
  `NETPLAY_LOBBY_CHECK_MS`, `NETPLAY_LOBBY_SWEEP_MS`, `NETPLAY_LISTED_SILENCE_MS`,
  `NETPLAY_MAX_LISTED_JOINS`, `NETPLAY_LISTED_JOIN_WINDOW_MS`.

Differences from the Node server, from the Workers runtime:

- The runtime answers ping frames (and the `ping` text) itself and gives the
  object no control frames. Thus there is no control-frame quota and no server
  heartbeat. Dead connections end with the TCP connection, the idle limit or
  the lifetime; a listed waiting host also ends when it stops sending `ping`.
- Workers WebSockets do not show the outgoing buffer size. The runtime buffers
  outgoing data; the per-player rate limit bounds it. The queue bound applies
  to the test-only delay queue.
- The 10,000-room-ID process bound does not apply; the retired markers delete
  themselves.

`npm run test:worker` runs the relay under `wrangler dev` (version pinned in the
test, same as the deploy job) with real WebSocket clients: rooms in
`tests/worker/netplay.test.mjs`, room lists in `tests/worker/lobby.test.mjs`
(the Node server runs the same cases in `tests/server/lobby.test.mjs`).
`tests/worker/lobby-object.test.mjs` runs the lobby object with a fake state
for the liveness check of rooms whose objects restarted, which `wrangler dev`
cannot trigger, and compares the name and address rules of both relays. The Durable Object
bindings and migrations of the test come from `deploy/wrangler.jsonc`. The deploy workflow
runs it before the build. To play a full match on a deployed site:

```sh
UQM_ORIGIN=https://urquanmasters.org/original/ npm run test:browser
```

With `UQM_ORIGIN` the browser test starts no local relay and skips the jitter
scenario, which needs a relay with test delays.

## Node reference integration-test API

```js
import { createNetplayServer } from './server/netplay.mjs';
const relay = createNetplayServer({
  distDir: './dist', // false disables static serving
  latencyPatternMs: [40, 0, 20] // deterministic test latency; preserves stream order
});
const address = await relay.listen(0, '127.0.0.1');
// relay.server is the HTTP server; relay.stats exposes aggregate counts only
// (rooms, connections, usedRoomIds, lobbyConnections, listedRooms).
// Run browser tests using http://127.0.0.1:${address.port}/.
await relay.close();
```

Constructor options also expose `allowedOrigins`, `maxPayload`, `maxBufferedBytes`, `maxRooms`, `maxRoomIds`, `maxPerIp`, `waitingMs`, `lifetimeMs`, `heartbeatMs`, `idleMs`, `listedWaitingMs`, `maxListedRooms`, `maxListedPerIp`, `maxLobbyConnections`, `maxLobbyPerIp`, `listedSilenceMs`, `maxListedJoins` and `listedJoinWindowMs` for bounded local tests. The heartbeat also checks that every listed room still waits with a connected host that sends `ping` texts (protocol pings do not show a frozen page, because the browser answers them). Artificial delay is a server construction option, never a client-controlled query parameter.

The WebSocket dependency is pinned in `package-lock.json`. API reference: [ws documentation](https://github.com/websockets/ws/blob/master/doc/ws.md).

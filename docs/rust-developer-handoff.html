01 Delivery status

The port covers both game engines: campaign logic, combat, ships, dialogue, saves, menus, resource management, rendering, audio/video orchestration, and threading. Work is isolated on a separate branch based on 783d8d3ce. A combined playable browser package has been built and tested locally.

Commit status, reviewed 20 October 2026: the Original and HD Rust port is committed as 84e963030, and the HD Online Melee integration is committed as 3e8597d4b. The tested implementation and handover have been pushed to GitHub on codex/rust-port. This document revision updates delivery status only; it does not change game code or claim a new gameplay test run.

The Rust branch is available on GitHub. Fetch codex/rust-port from vcorem/uqm-3do-web. This work has not merged the branch into main or deployed or released this Rust version.

HD netplay provenance: imported from main’s commit 5d7810ba5302803abe537f1b669d696a3af073ad, observed in main at 3ba129550. The complete HD engine was regenerated with networking enabled, preserving network-dependent layouts throughout the game. Main’s separate Cloudflare deployment work was not imported or deployed by this change.

This is a source port that preserves the C data model and algorithms. It retains substantial unsafe Rust. Most engine code was translated with C2Rust; selected shared modules were implemented manually and tested against the original C. Changing the source language does not by itself establish memory safety.

02 Architecture and implementation boundaries

The simulation runs on each client. For both editions’ Online Melee, the relay transfers an ordered binary stream between two clients; it does not run a central combat simulation.

ComponentLocation and responsibility
Original enginerust/uqm-engine-original/ — translated from 340 configured source units.
HD enginerust/uqm-engine-hd/ — translated from 350 units of the separately pinned MegaMod source, including 20 network/protocol units enabled for HD Online Melee.
Shared corerust/uqm-core/ — RNG, CRC, integer square root, fixed-point movement, angles, queues, geometry/clipping, and dirty regions. Replaces ten units in each engine.
PNG and Lua boundariesrust/uqm-png/ implements PNG integration in Rust. rust/uqm-lua/ protects error boundaries around the existing Lua interpreter.
Room relayrust/uqm-relay/ — the default backend of npm start. The Node reference server remains available through npm run start:node.
Dependencies and adaptersSDL2, OpenAL, libpng, zlib, Ogg/Vorbis, and HD's Lua remain native dependencies. Small C adapters handle entry, Emscripten compatibility, JavaScript string storage, and protected error boundaries.
Browser platformThe launcher, persistence, WebSocket bindings, and generated Emscripten runtime continue to use JavaScript.

Default builds link the Rust engine archive with no legacy C game object files. Each edition includes engine-language.json and link-inputs.json to record the implementation and link inputs. Original C sources remain available for provenance, licensing, and independent reference builds.

UQM_CORE=rust is the default. UQM_CORE=c builds the reference engine; UQM_CORE=hybrid retains the intermediate migration for diagnosis. The engine crates are separate workspaces from rust/Cargo.toml; the main workspace's unit tests and Clippy checks cover the maintained core and relay.

03 Critical fixes to preserve

AreaFailure and correction
Macros and ambient starsC2Rust macro reconstruction collapsed different MakeLinks invocations into an incorrect constant, erasing ambient star lists. Both engines were regenerated with --translate-const-macros none and --translate-fn-macros none. An actual-translator regression and a visual negative control now cover this failure.
PNG and Lua errorsSmall C guards protect operations that may longjmp. Errors propagate through Rust as normal returns; errors are rethrown from C only after Rust callbacks return. Tests cover out-of-memory failures, nested calls, readers, finalizers, and error handlers.
Initialization and allocationTranslated global tables initialize explicitly once. Allocation uses the existing Emscripten heap; alignments above eight bytes use aligned allocation. Tests cover alignment, zeroing, fragmentation, growth, and shrinkage.
Solar display orderingThe legacy PlanetDesc[-1] sentinel explicitly selects SunDesc[0], preserving draw order while keeping planet bounds checks.
Repeatable HD patch upgradesLater netplay patches change earlier patch context. Source updates are validated in a temporary staging tree before publication, including upgrades from the older CRC-patched cache. A failed patch leaves source files unchanged; repeated builds preserve unchanged files.
JavaScript integrationEM_ASM strings are emitted into the Emscripten-required data section through a dedicated adapter, with exact-byte validation.

Regeneration lives in scripts/rust-engine/. It pins tool versions and source inputs, verifies 19 reproduction-input hashes, and checks public exports. C2Rust is not needed for normal builds from the checked-in Rust sources. Changing the translator or regenerating engine code requires repeating the documented comparison and browser checks.

04 Build and run from a clean checkout

Run all commands in Bash, from the root of the Rust branch checkout. Prerequisites: Git, Make, Python 3.10+, Node.js 22+, Rustup, and native C build tools. macOS requires the Xcode command-line tools; Linux requires a working native compiler toolchain.

Receiving the code: fetch and select codex/rust-port from the GitHub repository, then verify that its history includes the full commit recorded in Section 08. The .tools/, dist/, and raw test-result directories are ignored by Git. Rebuild the package and rerun validation on the receiving machine.

A. Install the pinned toolchains

mkdir -p .tools
git clone --depth 1 https://github.com/emscripten-core/emsdk.git .tools/emsdk
.tools/emsdk/emsdk install 3.1.50
.tools/emsdk/emsdk activate 3.1.50

rustup toolchain install 1.85.1 --profile minimal \
  --component rustfmt --component clippy
rustup toolchain install "$(cat .rust-wasm-toolchain)" --profile minimal \
  --component rust-src --target wasm32-unknown-emscripten
npm ci

The SDK stays inside the project. If .tools/emsdk already exists, reuse it and verify its version instead of cloning again. Set EMSDK_PYTHON to a Python 3.10+ executable if the SDK installer needs it.

ToolPin and purpose
Native Rust1.85.1 — relay and native tooling.
Wasm Rustnightly-2025-02-01 with rust-src — C-variadic ABI and rebuilding Rust libraries with atomics/shared-memory support.
Emscripten3.1.50 — required for the final browser link. Toolchain changes must pass full linking and gameplay checks.

B. Build both editions and start the relay

./scripts/build-editions.sh
npm start -- --host 127.0.0.1 --port 10000

Open http://127.0.0.1:10000/. The first command builds both engines and packages the edition picker into dist/; separate engine builds are not required beforehand. The first server start builds the relay. Stop it with Ctrl-C.

Original is under dist/original/; HD is under dist/hd/. The current combined local output occupies about 916 MiB. Only the selected edition loads. HD has a large media bundle, so allow time and memory for its first load; these artifact sizes are not a measured bandwidth budget.

Start an online match

Both players choose the same edition. The host selects Create room and sends the generated invite URL; the guest opens that URL or pastes it into the same edition’s launcher, then clicks Join room. After pairing, both select Launch online Melee. Each player uses the arrow-key control template for their assigned fleet. HD invites retain the HD page path; do not replace them with a bare picker URL.

C. Diagnostic builds

# Original C reference, separate from the playable Rust package
UQM_CORE=c BUILD_OUTPUT="$PWD/.tools/c-reference" ./scripts/build-web.sh

# HD C reference (the first combined build prepares its pinned source/media)
UQM_CORE=c HD_BUILD_OUTPUT="$PWD/.tools/hd-c-reference" ./scripts/build-hd-web.sh

# Native relay only; no Emscripten required for this step
bash scripts/build-rust-relay.sh

When using the isolated toolchain under .tools, run source scripts/rust-env.sh before direct Cargo commands. The build scripts already do this. Use a separate checkout and origin to preserve the existing playable installation and saves.

06 Hetzner VPS handoff

This is a deployment specification for the receiving developer; it has not been executed on the server. Deploy the static browser package, a Linux relay executable, and an HTTPS reverse proxy with WebSocket support. The current protocol requires no database, Redis, or TURN service. Start with one relay instance: room state is local to that process.

ItemServer requirement
Linux relay binaryBuild uqm-relay for the VPS's actual Linux architecture. The local macOS binary is not deployable to Linux. Rust is needed at build time; the ready binary does not require Node, Cargo, or Emscripten to run.
Game artifactsCopy the complete combined dist/, including both editions and media, for example to /srv/uqm/web. Keep JS, Wasm, worker, and data files from the same build together. Browser dependencies do not require a separate server-side Lua installation.
Managed serviceUse a service manager such as systemd, an unprivileged service account, restart handling, and logs. Bind the relay to loopback behind the proxy.
Domain and TLSAfter choosing the domain and configuring DNS, provision HTTPS with certificate renewal. Pass the exact public --origin, without a trailing slash.
RoutingServe assets and /netplay/ on the same origin, with WebSocket upgrade forwarding. Both multiplayer paths are at the site root even when the game is served from /original/ or /hd/. Forward the entire /netplay/ prefix, including HD.
Isolation headersPreserve Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp. Serve Wasm as application/wasm. Verify crossOriginIsolated through the public domain.

Build on a compatible Linux build host, from the repository root

cargo build --manifest-path rust/Cargo.toml \
  -p uqm-relay --release --locked

Example service command after copying the Linux binary and assets. The domain below is a placeholder.

/srv/uqm/bin/uqm-relay \
  --host 127.0.0.1 --port 10010 \
  --origin https://game.example \
  --dist /srv/uqm/web

Each room has exactly two players. Defaults include 128 active rooms, 16 connections per IP, 64 KiB maximum messages, and 256 KiB outgoing/queued data per direction. Waiting rooms expire after two minutes; paired rooms expire after 15 minutes without game data or four hours total. Restarting the process ends all active rooms.

Resolve proxy admission before public exposure. The relay does not trust forwarded headers for client IPs. Behind one proxy, all users may share the same 16-connection limit. There is currently no production CLI flag to change this limit; --test-options is test-only. Also, after 10,000 distinct room IDs in one process, new rooms are rejected until restart.

Original uses /netplay/<room>?role=host|guest; HD uses /netplay/hd/<room>?role=host|guest. The room token is exactly 32 lowercase hexadecimal characters. Edition is part of both active and retired room identity, so matching tokens across editions cannot pair or disconnect each other. Both editions share the relay’s capacity limits. An invite link grants access to the room. There are no accounts, public lobby listings, or persistent match records. A disconnect ends the room and requires a fresh invitation. The Node reference server does not need to run alongside Rust.

Current static responses use Cache-Control: no-store; caching and a public download workflow require deliberate follow-up. A downloadable browser bundle still needs a suitable local web server—opening the game directly as a file:// URL will not provide the required shared-memory environment.

07 Recommended next steps

  1. Fetch the branch and reproduce the build. Build on a second machine and verify a passing run of the expanded Linux CI workflow. Retain the hashes and reports from that build.
  2. Create a server staging environment. Build the Linux relay, deploy the full package to a test domain, and verify HTTPS, browser isolation, media loading, and WebSocket routing.
  3. Test two computers on separate networks. For each edition, exercise room creation/joining, fleet selection, a complete match, rematch, disconnects, and persistence. Check latency and the real proxy admission limits.
  4. Run longer gameplay validation. Complete a campaign path and exercise dialogue branches and situational ship abilities beyond the short smoke checks. Review media playback and the 3DO compatibility checklist.
  5. Prepare a versioned release. After validation, package consistent artifacts and document save-origin changes, upgrade/rollback behavior, and hosting operations. Idiomatic Rust and memory-safety improvements can proceed incrementally behind the comparison suites.

Still unverified: completion of the entire campaign, all dialogue branches and ability outcomes, every 3DO fidelity detail, internet play on two physical computers, and memory safety. Passing local tests and compiling both engines do not establish those claims.
